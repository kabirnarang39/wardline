# Wardline v0.1 Design

## Purpose

Wardline is an open source control-plane proxy that sits between AI agents and
everything they call — MCP servers today, LLM providers and other agents
later. v0.1 is the smallest useful slice: prove the core loop (intercept,
decide, forward-or-reject, record) for MCP tool calls, with a static policy
file and no external dependencies beyond the standard library and a YAML
parser.

Full long-term product vision, architecture, and roadmap (v0.5 → v2.0) live in
the opportunity report this project originated from; this spec covers only
v0.1.

## Scope

**In scope for v0.1:**
- Single Go binary, two subcommands: `wardline serve`, `wardline validate-policy`.
- Reverse proxy in front of one upstream MCP server.
- Static YAML policy file: allow/deny rules keyed by a static per-agent
  identity token and MCP tool name.
- Structured JSON audit log, one line per proxied request, written to
  stdout or a file.

**Explicitly out of scope for v0.1** (later versions, per the product roadmap):
short-lived/SPIFFE identity issuance, OPA/Cedar policy engines, budget
enforcement, approval workflows, web UI, Postgres, OpenTelemetry, multiple
upstreams, multi-tenant RBAC.

## Architecture

Clean Architecture, dependency rule inward, sliced by feature per
`CLAUDE.md`. Three features for v0.1, each with its own domain/usecase/adapter:

```
internal/features/proxy/
  domain/    Request, Decision entities
  usecase/   intercept incoming JSON-RPC, extract tool name + identity, ask
             policy for a decision, forward or reject
  adapter/   HTTP reverse-proxy server (net/http + httputil.ReverseProxy)

internal/features/policy/
  domain/    Rule, Scope entities; Engine interface (Evaluate(identity, tool) Decision)
  usecase/   rule matching logic (first-match allow/deny, default deny)
  adapter/   YAML file loader implementing Engine

internal/features/audit/
  domain/    Entry entity
  usecase/   build an Entry from a proxy Decision + request metadata
  adapter/   JSON-lines writer (stdout or file, chosen by config)

internal/platform/
  config/    load + validate the top-level YAML config (upstream URL,
             policy file path, audit output, listen address)
  flags/     flags.Provider interface + static config-map implementation
             (no flagged features exist yet in v0.1 — this exists so v0.5+
             features have a place to plug into from day one)

cmd/wardline/main.go   composition root: parse CLI args, load config, wire
                       adapters into usecases, run serve or validate-policy
```

## Data flow

1. Agent sends an HTTP request (MCP JSON-RPC) to Wardline's listen address.
2. `proxy/adapter` receives it, `proxy/usecase` parses the JSON-RPC envelope
   to get method + tool name, reads the identity token from a request header.
3. `proxy/usecase` calls `policy.Engine.Evaluate(identity, tool)`.
4. **Allow** → `proxy/usecase` forwards the original request to the
   configured upstream MCP server, pipes the response back to the agent.
   **Deny** → `proxy/usecase` returns a JSON-RPC error response to the agent,
   upstream is never contacted.
5. Either path: `audit/usecase` builds an `Entry` (timestamp, identity, tool,
   decision, latency) and `audit/adapter` writes it as one JSON line.

## Error handling

- Policy file fails to parse or has a malformed rule at startup → `wardline
  serve` refuses to start, prints validation errors to stderr, exits
  non-zero. `wardline validate-policy` runs the same validation standalone
  for CI use.
- Upstream MCP server unreachable or times out → respond 502 to the agent,
  write an audit entry with `decision: error`.
- Malformed JSON-RPC request from the agent → respond 400, write an audit
  entry with `decision: error`.
- Audit writer failure (e.g. disk full) → log to stderr and continue serving
  requests; never let audit-write failure block or crash request handling
  for a security proxy, dropped audit lines are recoverable, dropped
  availability isn't.

## Testing

- `policy/usecase`: unit tests for rule matching — exact match, wildcard
  tool name, default-deny fallthrough, first-match-wins ordering.
- `proxy/usecase`: unit tests with a fake `policy.Engine` and fake upstream,
  covering allow/deny/error paths.
- `audit/adapter`: golden-file test asserting the exact JSON-line shape.
- One end-to-end test in `cmd/wardline`: real binary, mock MCP server,
  temp policy file, asserts an allowed call reaches the mock server and a
  denied call doesn't.

## Config file shape (v0.1)

```yaml
listen: ":8080"
upstream: "http://localhost:9000"
policy_file: "./policy.yaml"
audit:
  output: stdout   # or a file path
```

```yaml
# policy.yaml
rules:
  - identity: "agent-abc123"
    tool: "read_file"
    effect: allow
  - identity: "agent-abc123"
    tool: "*"
    effect: deny
default: deny
```

## Out-of-scope call-outs (tracked for later, not this spec)

- SPIFFE/short-lived identity issuance replaces the static header token —
  v1.0 per the product roadmap.
- OPA/Cedar policy backends replace the YAML matcher — v0.5/v1.0. The
  `policy.Engine` interface is written now so this is a new adapter, not a
  rewrite (OCP).
- Budget enforcement, approval workflows, web UI, multi-upstream support —
  v0.5+.
